# MySQLScriptV4 设计说明

## 0. 目标

把“造数”拆成三件互不干扰的事：

1. **用户/AI 只描述数据长什么样**（DDL + 每列规则 + 父子关系 + 每父几行）；
2. **框架保证写进去的数据正确、可重放、可续跑**；
3. **写之前能检查，写之后能核对**，而不是“跑完看有没有报错”。

非目标：通用 ETL、跨库同步、复杂业务约束推导、自动读库猜关系。

## 1. 为什么从 V3 的“生成器”改成“声明式表定义”

V3 的模型是：每张表写一个 `generate_data(ctx, parent_rows)` 生成器。它简单，但把三件事又揉回给了用户：

- **列顺序**：行是手写元组，DDL 加一列就可能错位；
- **外键**：子表要自己从父行里挑主键，取错列不会报错，只会在 `verify` 时才知道；
- **行数**：`per_parent` 是假的，比例写在循环里，`plan` 算不出总量。

V4 把“每行怎么拼”收归框架：用户只给 `{列名: 规则}`，框架按 DDL 顺序拼行、按 `fk` 填外键、按 `per_parent` 推导行数。
于是**一大类错误在结构上不可能发生**，剩下的错误 `plan` 能在不连库的情况下抓出来。
这也正好匹配“把 DDL 和关系丢给 AI，让 AI 生成脚本”的用法：AI 只需要填一张声明式的表，而不是写控制流。

## 2. 分层

```text
spec 文件（用户/AI 写）          框架
┌─────────────────────┐   ┌──────────────────────────────────────────┐
│ DDL 常量             │   │ ddl.py    解析列/类型/主键/默认值          │
│ Table(...) × N       │──▶│ spec.py   校验 + 依赖图 + 行数推导 + 计划  │
│ TABLES = [...]       │   │ gen.py    任务内流式生成（父→子→孙）       │
└─────────────────────┘   │ sink.py   批量 INSERT / 进度表 / verify    │
                          │ engine.py 任务、事务、线程池、重试、进度    │
                          │ cli.py    plan / run / verify              │
                          └──────────────────────────────────────────┘
```

`plan` 完全是离线的：解析 DDL、检查字段覆盖、抽样生成、跨任务探针，**不打开数据库**。
`run` 才连接数据库；`verify` 只读。

## 3. 任务模型

```text
任务 k = 根表行区间 [k*task_rows, min((k+1)*task_rows, rows))
```

一个任务同时是：

- **一个事务**：任务内父表、子表、孙表的全部批次一起提交；
- **一个并行单位**：任务之间根表行号不重叠，无共享状态；
- **一个续跑单位**：`_dataforge_tasks` 里一行记录。

任务内顺序是拓扑序（父 → 子 → 孙），按批流动：

```text
root 批 ──写入──▶ 用这一批父行生成 child 批 ──写入──▶ 用这一批子行生成 grandchild 批 ──▶ …
```

消费者拉一批、生产者才产一批，天然背压。任一 worker 同时只持有“当前这一批”，
所以内存上限 = `workers × batch_rows × 行宽`，与总行数无关。

## 4. 确定性语义

每张表在任务内的随机流**只播种一次**：`Random(f"{seed}|{表名}|{任务号}")`，整段任务共用。

由此得到：

| 改动 | 数据是否变化 |
| --- | --- |
| `--workers` 1 → 8 | 不变 |
| `--packet-mb` / 自动分批（batch_rows） | 不变 |
| 重跑同一任务 / 失败重试 | 不变 |
| `--task-rows` 改变 | **会变**（任务边界变了） |
| `--seed` 改变 | 会变 |
| 改了字段规则但 `SPEC_VERSION` 没 +1 | 会变，而且续跑不会察觉 |

前三条是 V3 的 bug（每个父批次重新播种，导致子表数据成块重复、且随 batch_size 变），V4 用“任务级 RNG + 每表独立 Row”修掉。

`task_rows` 参与签名，改了就不允许拿旧进度续跑；字段规则是代码，框架无法可靠哈希，
所以用显式的 `SPEC_VERSION` 兜底——这是有意的取舍，文档和错误提示都会提醒。

## 5. 事务、进度与恢复

### 5.1 进度表放在目标库里

```sql
_dataforge_runs (run_id PK, signature, created_at)
_dataforge_tasks(run_id, task_id, row_count, finished_at, PK(run_id, task_id))
```

每个任务提交数据时，**把进度行插在同一个事务里**。于是：

- “数据已提交但进度没记”这个窗口不存在；
- 进度天然绑定目标库，换库/删表/改行数不会误判（V3 的 checkpoint 文件就踩过这个坑）；
- 不需要额外的 checkpoint 文件、不需要 fsync 文件、不会在仓库里留 `.v3_checkpoint.json`。

`run_id = sha1(signature)[:12]`，签名包含：
`SPEC_VERSION`、根表行数、`task_rows`、`seed`、目标库标识（SQLite 绝对路径 / MySQL host:port/db）、
每张表的 DDL 哈希、`fk`、`per_parent`、列清单。

### 5.2 语义

| 操作 | 行为 |
| --- | --- |
| 新运行，同签名记录已存在 | 报错：加 `--resume` 或 `--wipe` |
| `--resume` | 跳过 `_dataforge_tasks` 里已完成的任务 |
| `--resume` 但目标库没有记录 | 报错（不会悄悄全量重跑） |
| `--wipe` | 清空数据表 + 清掉该 `run_id` 的进度，然后重跑 |
| `--wipe --resume` | 直接拒绝（清空 + 跳过 = 空库） |

进程在任意时刻被杀：已提交的任务有进度行，未提交的任务没有，续跑只会补后者。
“提交成功、进度行没写”不可能发生，因为它们在同一个事务里。

## 6. 失败与重试

| 异常 | 处理 |
| --- | --- |
| 锁等待 1205、死锁 1213、连接断开 2003/2006/2013/2014、连接数满 1040、实例只读 1053 等 | 回滚整个任务，退避后重试（默认 3 次） |
| SQLite `database is locked/busy` | 同上 |
| 1153 包过大 | 发送前按实际值估算，超限就缩批重试；真收到 1153 时连接通常已被服务端断开，丢弃连接、把 `batch_cap` 减半、整任务重来（最多 8 次） |
| 主键冲突、列超长、枚举越界、NOT NULL、规则抛错 | **不重试**，任务立即失败 |
| 任务内行数与计划不符 | 提交前抛错并回滚 |

默认“一个任务失败就停止提交新任务”（`--keep-going` 可关闭）。
已经在跑的任务会在下一批之前看到停止信号并回滚，不会留下半截数据。

## 7. 批量与包大小

- MySQL：显式多值 `INSERT ... VALUES (...),(...)`，SQL 模板按 `(表, 行数)` 缓存，一次 `execute` 一次往返。
- SQLite：`executemany` + 单行占位符。
- 每批行数 = `min(max_batch_rows, packet_bytes // 估算行宽)`，`Table.batch_rows` 可覆盖。
  行宽按类型估：int 8B、decimal 12B、datetime 19B、varchar `min(len,64)+2`、text/blob 32~40B。
- **发送前再按实际值估一次**（`_params_bytes`：ASCII 按字符数、非 ASCII 按 4 字节/字符、二进制按 2 倍），
  超过 `packet_bytes` 直接抛 `PacketTooLarge`，由引擎缩批重试。这样不会把 80MB 的语句发给
  `max_allowed_packet=64MB` 的服务端——那种情况服务端会直接断连，客户端再拆批就晚了。
- 连接按 worker 复用（线程本地），任务失败/连接断开才丢弃重连；`SET SESSION` 每条连接只执行一次。

## 8. 校验分六层

| 层 | 时机 | 抓什么 |
| --- | --- | --- |
| 结构校验 | `Spec` 构造/`plan` | 表名重复、单根、父表对象、`fk` 是否存在、列覆盖、未知列（带拼写建议）、生成列、`SKIP` 用在主键/外键、`per_parent` 写法 |
| 类型校验 | `plan` 抽样 | 字符串超长、枚举越界、NOT NULL、Decimal 精度/小数位、外键列比父键短 |
| 语义探针 | `plan` | 跨任务采样主键，抓“子表拿 `r.i` 组键”这类只在多任务时暴露的错误 |
| 目标表对照 | `run` 连库后、`wipe` 前 | 表是否存在、列是否缺失、类型/长度/精度/生成列是否与 DDL 一致；不一致直接停，**不清数据** |
| 运行期 | 每个任务提交前 | 行数 == 计划；首行全量校验（`--check all` 可全量，`--check none` 可关） |
| 事后 | `--verify` / `verify` | 每表行数、孤儿外键（LEFT JOIN）、重复主键（`COUNT - COUNT(DISTINCT)`） |

`plan` 的样例是“真生成”的，不是 mock：规则抛错、返回错类型都会在样例阶段暴露。

## 9. 性能

本机 Python 3.13；SQLite 与 MySQL 都是真实写入（MySQL 26.10.0 / PyMySQL 1.2.3 / 127.0.0.1 / InnoDB）。

| 场景 | 结果 |
| --- | --- |
| 生成 10M 行，确定性规则 | 6.8 s / 1.46M 行/s |
| 生成 10M 行，示例规则（加权/金额/时间/可空） | 27.6 s / 363k 行/s |
| SQLite 1M 行，与 V3 同规则、同为 4 workers | V4 3.93 s，V3 3.84 s |
| SQLite 2M 行，示例规则 | 10.5 s / 190k 行/s |
| MySQL 1M 行（100k 用户，8 workers） | 6.1 s / 163k 行/s |
| MySQL 10M 行（1M 用户，8 workers） | 写库约 63 s，端到端 98.6 s（含 verify），约 159k 行/s |
| MySQL `verify` 10M 行 | 33.8 s |
| 峰值堆，1M 行 4 workers / 8 workers | 20.7 MB / 40.6 MB |

MySQL 10M 行期间 `Innodb_row_lock_waits=0`、重试 0 次；`task_rows=5000` 与 `20000` 的差距不到 5%，
本地小库上 5000 略快（事务更短、锁持有时间更短）。

吞吐瓶颈按顺序是：**规则里的随机调用 > 数据库写入 > 引擎调度**。
每行一次 `randint/uniform/pick` 大约 0.3~0.5 µs，10M 行就是几秒；所以示例规则的 363k/s 是规则成本，不是引擎成本。

引擎侧为省时间做的几件事：

1. 每张表在 `plan` 阶段编译一个专用行构建函数（`exec` 生成元组字面量），去掉逐列循环和 `is_fk` 分支；
2. 外键用预计算的 tuple 下标取值，不做列名字典查找；
3. `Row` 和 `ParentView` 每表/每行复用，不分配字典；
4. 每表任务级 RNG 只建一次；
5. 连接复用、SQL 模板缓存、按字节分批。

## 10. 与 V3 的对照

| 关注点 | V3 | V4 |
| --- | --- | --- |
| 用户写什么 | 每表一个 yield 生成器 | 每表一张“列 -> 规则”表 |
| 列顺序 | 手写元组，可能错位 | 框架按 DDL 组装 |
| 外键 | 生成器自己从父行取 | 框架按 `fk` 自动填 |
| 行数 | 生成器自己控制 | `rows × per_parent` 推导，可预估 |
| 写前检查 | 列数、行数 | 列数、列宽、枚举、精度、外键长度、跨任务主键 |
| 进度 | JSON checkpoint 文件，与库无关 | 目标库内的进度表，同事务 |
| 每任务连接 | 每任务新建 + 5 条 SET | 线程本地复用，SET 一次 |
| RNG | 每个父批次重新播种（数据成块重复） | 任务级单流（与 batch/workers 无关） |
| 失败处理 | 所有异常都重试 | 只对连接/锁类重试 |
| 失败任务 | 保留已提交批次 | 整任务回滚 |
| 吞吐（同规则 SQLite） | 257k 行/s | 255k 行/s（多了校验和进度行，基本持平） |
| 内存 | O(workers × 批) | O(workers × 批)，4 workers 约 20 MB |

## 11. 取舍清单

1. **单根表**：换来“一个任务 = 一个事务 = 一个续跑单位”的干净语义；无关的表拆文件。
2. **子行只能引用同任务父行**：换来外键必然闭合、任务可并行；代价是不能跨任务做 M:N。
3. **显式主键、不回读自增**：换来重跑幂等和可续跑；代价是自增表也要手写 id。
4. **进度表在目标库**：换来原子性与换库安全；代价是需要建两张 `_dataforge_*` 小表。
5. **规则代码不参与签名**：换来不误判；代价是改规则要人工 +1 `SPEC_VERSION`。
6. **SQLite 只做代理**：换来无 MySQL 也能验证生成与事务；代价是索引/约束/默认值不完全等价。
7. **批大小自动按字节估**：换来不撞 `max_allowed_packet`；代价是行宽估算保守，批可能偏小。

## 12. 后续可做

- 更多 MySQL 版本 / 云数据库（RDS、Aurora）上的参数扫描；
- `per_parent` 为区间/函数时的“总行数精确预估”（当前是动态，`verify` 只核对外键和主键）；
- 多根表 / 多列主键 / 跨任务引用（会破坏当前任务模型，需要重新设计）；
- 把 `plan --json` 接进 CI，对 spec 做回归（同一份 spec 的样例哈希固定）。
